# 持续工作流

在目标需要持续实现、用户反复派发相似任务，或已授权重构流程时读取。一次性任务不必套用本文件。

## 从目标到能独立运行的循环

先确定业务结果、适用范围及可接受的行动，再补齐下列要素。持续自主不等于拥有无限权限；用验证和异常分流减少人工介入。

| 要素 | 需要落实的内容 |
| --- | --- |
| 目标与触发 | 何种事件、时间或阈值启动，何时算本轮完成 |
| 原始输入 | 来源、字段、更新频率、数据可用时点、访问与隐私边界 |
| 上下文映射 | 业务实体或版本怎样对应原始记录、配置和可修改对象 |
| 执行环境 | 必要计算机、系统、软件、连接器及权限；独立复现与验证需要什么 |
| 持久状态 | 已处理标识、游标、假设版本、历史证据和本轮结果 |
| 行动与验证 | 可自动做什么，成功检查是什么，失败后怎样回退或改道 |
| 异常与升级 | 缺数据、验证失败、超预算或超权限时保留什么证据，何时需要用户处理 |
| 再次进入 | 如何避免重复执行、重复通知和失败循环，下一轮如何读取已有状态 |

先接通“输入—行动—外部验证”这一条最短闭环，再扩展覆盖范围。若只能设计，交付字段、执行逻辑、验证方法和缺失依赖；区分设计、局部原型、已配置和实际运行状态。

## 示例：从修复一次崩溃到持续降低崩溃

接入崩溃报告，建立“应用版本—构建—代码提交”映射，并准备实际受影响的系统环境。循环执行去重分组、独立复现、定位修复、运行回归、记录结果；复现不出或回归失败时保留证据，进入异常分支。

只在获授权的范围内实施修改或发布。输出“暂无已知未处理崩溃”时要注明数据覆盖与时间窗口，不能承诺绝对不会崩溃。

## 在替换旧流程前证明价值

1. 用历史资料重放：每个历史时点只使用当时可获得的信息，避免未来数据泄漏。
2. 比较既有方法与新机制的发现时间、误报、漏报、决策或修复质量和总成本。
3. 在适当周期内与旧机制并行，验证前瞻效果和实际工作量；季度业务场景可按用户预算安排一个季度。
4. 按预先明确的通过条件决定推广、修正或停止。回测成功不能冒充前瞻运行完成。

用户仅要求方案时不自动创建长期任务。用户已要求持续运行且工具支持时配置真实机制，并验证至少一次输入、动作和反馈；周期较长的结果须等待实际发生，不能提前宣称。
