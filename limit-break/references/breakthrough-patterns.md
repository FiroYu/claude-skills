# 突破路径与示例

## 选择能改变瓶颈的操作

只选与当前问题有关的操作，不把下表变成逐项汇报。

| 默认假设 | 值得尝试的路径 | 必须验证的代价 |
| --- | --- | --- |
| 每次请求都必须从头计算 | 增量计算、预计算、复用中间结果 | 新鲜度、存储、失效策略 |
| 每个步骤都必须执行 | 删除无价值步骤、改成条件触发 | 被删步骤是否承担关键质量保证 |
| 必须先完成全部工作才能反馈 | 分阶段交付、渐进呈现、提前消除关键不确定性 | 首次可见结果和完整结果是否被混淆 |
| 必须逐个处理 | 批处理、并行、改变任务粒度 | 资源竞争、尾延迟、失败隔离 |
| 只能在当前环节优化 | 把工作移到上下游、重设输入或接口 | 谁承担新增成本、问题是否只是转移 |
| 信息越多越有说服力 | 围绕决策压缩信息、可交互证据、渐进披露 | 是否遗漏反证、受众是否正确理解 |
| 观察到的关系就是原因 | 时间切分、自然实验、适当的对照设计 | 混杂、数据泄漏、外推条件 |
| 只能一次性给出固定方案 | 先试探、按反馈分流、持续监测与纠偏 | 反馈延迟、探索成本、错误累积 |

## 示例一：网站从10秒到0.2秒

先定义“加载完成”：首字节、首屏可见还是完整可交互。保留原指标，分别报告辅助指标，避免用首屏时间替代完整加载时间宣称达标。

读取真实请求瀑布、服务端追踪、资源体积及冷暖缓存数据。区分计算、传输、串行依赖和主线程阻塞。探索压缩与代码拆分、预计算与缓存、重构关键依赖等不同机制。

挑选一条路径实现最小改动，用相同页面内容、设备、网络和缓存口径复测，报告样本与延迟分布。若只有暖缓存达到0.2秒，明确适用条件，并继续检验冷启动瓶颈；不要称全部场景均已达标。

## 示例二：把季度复盘变成提前发现问题的机制

保留用户需要的PPT，重新聚焦“提前发现异常并作出资源决策”。挑战“只能按季度看汇总数字”的惯例。

探索决策驱动的复盘、基于原始事件的异常预警、按关键假设更新的资源配置机制。让每条路径说明它怎样改变发现问题或作出决策的时间。

若用户认为流失来自新手引导，先核对用户分群、价格变化、渠道质量和产品故障等反例。发现阶段仅使用当时可获得的信息，在后续时间窗口检验；回测只能支持历史有效性，前瞻并行试运行才能进一步检验实际价值。

没有原始数据时，交付数据字段、可执行分析逻辑、一个决策页样稿及试运行设计。不要虚构流失原因、预警提前天数或收益数字，也不要仅说“需要更多数据”。

## 示例三：让一场品牌发布会更有记忆点

把“惊艳的PPT”改写为“让目标观众记住品牌的一项独特价值，并愿意传播或采取行动”。保留场地、预算、时长和品牌事实。

探索机制不同的体验：用可核验的事实揭示一个反直觉结论；让观众的选择改变现场呈现；用贯穿全场的叙事兑现最终揭晓。为最强路径交付一段能实际演示的开场脚本或关键页面，而非只给“沉浸式、国际化、震撼”等形容词。

用小样测试观众能否复述主张、理解证据和说出下一步行动。作者自评“感染力9分”不构成验证。无法测试时，提交真实样稿、待检验的效果假设和测试问题，避免保证传播量。

## 换路时的检查

- 候选是否改变了解题机制，还是只换名字或增加资源？
- 最大胆的路径被淘汰，是因为有证据，还是因为不熟悉？
- 能否先检验决定成败的一小部分，而不承担完整实施成本？
- 结果未达标，究竟推翻了目标、某条路径，还是一个实施细节？
- 是否仍有一条在相同硬约束下值得验证的路径？
